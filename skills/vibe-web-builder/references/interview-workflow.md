# 自适应访谈

## 每轮决策

1. 从当前输入、旧文档和可验证代码中提取事实，合并重复内容。
2. 在事实表保存来源与状态：Confirmed 是用户明确给出的内容，Proposed 是 AI 建议，Assumed 是低风险默认，Unresolved 是关键缺失或冲突。字段确认不代表整份总结已确认。
3. 检查用途、用户、页面、功能、视觉五项；只选最妨碍下一步的 1–3 个缺口。优先业务结果，不问实现技术。
4. 一次回答多项则同时更新。“你决定”产生建议与理由，不能伪造用户确认。用户想少问时集中给默认建议并一起确认。
5. 五项明确或可低风险补齐且无关键冲突时停止提问。私密数据归属、收费方式等不能以默认跳过。

模糊“想建个网站”：先问主要用途，可给“介绍自己 / 展示作品 / 在线工具 / 由 AI 推荐”等易懂选项，不一次丢五项问卷。

完整“摄影作品集，给潜在客户看，首页/作品/联系，暗色大图，无登录、只展示邮箱，只要方案”：直接提取并总结，不再问受众、模式或是否需要数据库。

## 条件补问

| 实际能力 | 影响业务的补问 |
|---|---|
| 登录与多人数据 | 谁能看/改什么？是否需跨设备长期保存？ |
| 支付 | 卖什么、何时交付、失败/退款怎么处理？接服务前另获授权。 |
| AI/第三方 API | 输入输出、失败体验与费用约束；不在聊天索密钥。 |
| 投稿 | 谁能发布、是否审核、删除由谁决定？ |

没有这些能力就不问。技术方案在检查现有架构后自行推荐。

## 需求总结

必须包含目标、用户、页面、功能、视觉、默认假设、未解决项；区分四类状态，说明 MVP 范围。模式未明确时给规划/开发选择，不重问已选模式。模式选择本身不算总结确认。

请求“确认需求 / 修改 / 补充”。用户接受本轮总结后，将 confirmation 设 confirmed，confirmed_revision 设当前 revision，confirmation_evidence 记用户确认原意与时间。未答复保持 pending，可以整理文档但不能跨过门槛。
